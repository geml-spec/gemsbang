## 0. 一句话

中继存文档、盖章、排队、解析引用，不跑模型、不托管资金、不经手密钥、不存包的字节。每个人一个守护进程把中继镜像成本机的 GEML 文件，各宿主只读写本机文件；托管 agent 是同一个守护进程加一个无头宿主；访客网页和手机桥只有访客等级和收件箱动作。

## 1. 三个选择

### 1.1 agent 的身体怎么连上中继

| 方案 | 做法 | 代价 |
|---|---|---|
| 钩子里轮询 | 插件的钩子模块用 `$.http.fetch` 每隔几秒拉队列，写操作走现有的 bridge CLI | 钩子沙箱里没有 Node、没有长连接，延迟等于轮询间隔；会话关了 agent 就失联 |
| **常驻守护进程（选定）** | 每个人一个 `gemworks connect`，是现有 CLI 的子命令：对上一条 WebSocket 到中继，对下把这个人的场所、队列、收件箱镜像成 `~/.gemworks/im/` 下的 GEML 文件；各宿主只读写本机文件、经 bridge 调它 | 要有一个进程活着：launchd / systemd / Windows 服务，或 bridge 第一次用到时拉起（§8） |
| 每个宿主直连 | 四个适配器各自实现中继协议 | 四份代码 |

守护进程为主，钩子轮询作为没有守护进程时的降级。这和现有结构一致：钩子模块不带 Node，重活都在 CLI（`src/bridge.ts`）。托管 agent 是同一个守护进程加一个无头宿主，没有第二套代码。

### 1.2 中继存什么

| 方案 | 做法 | 代价 |
|---|---|---|
| **GEML 原生（选定）** | 每个场所、账号、队列、卡、账本、信号链各是一份 GEML 文档，消息和实物是有 id 的块；embed 的 `src=` 字面上就是这份文档；每份文档自己是哈希链 | 查询靠一个从文档派生、可重建的索引（SQLite 加全文） |
| 数据库加边缘导出 | 常规表存，读时拼成 GEML | 两个事实来源；embed 要映射表；哈希链另算 |

GEML 原生让主文档第十条「引用不复制」字面成立：地址指向的就是那个块，`geml get` 能直接读，离线镜像和服务器上是同一种文件。索引只是加速，删了能重建。

### 1.3 托管 agent 跑在哪个宿主上

| 方案 | 代价 |
|---|---|
| **pi agent（选定）** | 适配器已有（`src/hosts/pi/`）；无头、模型无关、按 API key 计费，天然有接单资格；最薄 |
| DSH | 适配器已有，自带 web GUI；但它是完整的应用，服务器上跑一群实例偏重 |
| Claude Agent SDK | 要写第四个适配器 |

DSH 适合用户自己在本机跑，不适合平台托管。

## 2. 中继

### 2.1 职责

身份与登录；场所与成员；文档存储与盖章；embed 的解析与权限检查；每个 agent 账号一条队列；在场；包的索引（不存字节）；账本与信号链的追加；联邦开关。**不做**：跑模型、托管资金、经手密钥、存包的字节。

### 2.2 数据模型

八类文档，都是普通 GEML：

| 文档 | 内容 | 写入者 |
|---|---|---|
| `people/<id>.geml` | 主页、名下 agent、策略块、信任名单、钱包指针 | 本人 |
| `agents/<id>.geml` | 主页、常驻策略、接单声明、会话登记（宿主、登录种类、在场） | 主人与它的守护进程 |
| `queues/<agent>.geml` | 追加式：每条队列项一个块，读入和回应是后续的标记块 | 中继追加，守护进程标记 |
| `venues/<id>.geml` | meta（种类、成员、策略、bot 密度）；`#announce` 群公告；决策块；消息块 | 成员经中继 |
| `cards/<id>.geml` | 任务卡块、状态修订块（journal 式）、交付物清单块 | 委托方与接单方经中继 |
| `ledger/<person>.geml` | 哈希链条目 | 只有中继 |
| `signals/<agent>.geml` | 信号链，含撤回标记 | 发布方经中继 |
| `packages/<sha>.geml` | 包的清单与存放位置（git 远端、对象存储、对等拉取） | 上传方经中继 |

一条消息是一个块，属性由中继盖：

```geml
=== message {#m-000417 speaker="agent:xiaoping@john" session="cc-7f3a" kind="report" at="2026-10-30T09:12:04Z" prev="sha256:…" hash="sha256:…" thread="#m-000402"}
测试跑完了，三条过两条。
=== embed {src="https://relay.example/john/journals/t-42.geml#rev-14"}
===
```

- 线程不是文档，是 `thread=` 属性上的查询。
- 访客私信是一个两人场所。
- 私信（会话本身）不在中继上：只有 agent 发出去的东西和盖过章的事实到中继（主文档规则 4）。
- 每份文档的哈希链：块的 `hash` 算在规范化后的字节（LF、去尾随空白）上，含 `prev`；`prev` 指向同一文档的上一块。

### 2.3 地址

`https://<中继>/<所有者>/<文档>.geml#<块>`。

- embed 的 `src=` 就是它；钉住的加 `rev=`（journal 修订）或 `hash=`。
- 本机镜像在 `~/.gemworks/im/<中继>/<所有者>/<文档>.geml`，`geml check --root ~/.gemworks/im` 离线也能解析引用。
- 地址里带着中继的主机名，跨中继的 embed 不用改格式。

### 2.4 盖章

每个块追加时中继写 `at`、`speaker`、`prev`、`hash`。`speaker` 来自请求用的令牌：本人令牌（桌面端的输入框、访客网页、手机桥）或 agent 令牌（守护进程替宿主的工具发的）。在桌面插件里两条管道都经过守护进程，但钩子模块知道一条消息来自 `prompt.submit` 还是来自工具调用，守护进程按这个选令牌。中继信守护进程的选择：守护进程是宿主的一部分。

登录种类（订阅 / API / 自托管）由守护进程报告，中继记为「守护进程报告」。谎报是主人的违约，不是技术问题。

### 2.5 协议

三条通道：

| 通道 | 做什么 |
|---|---|
| 写（HTTPS） | 追加块、认领、标记。幂等：客户端生成块 id，重发不重复 |
| 读（HTTPS） | 整份文档，或 `?block=#id` 取一个块；和 CLI 的 `list / get / find` 同一套动词。每次读都过权限，无权的块回存根 |
| 订阅（WebSocket） | 按场所、队列、收件箱推送新块 |

登录：本人用邮件验证码（passkey 后加，§8）；agent 令牌由主人签发、按 agent 作用域、可吊销；会话登记时守护进程带上宿主和登录种类。

### 2.6 联邦开关

每个中继一个设置：`open`（任何中继的用户可互通）、`allowlist`、`closed`。v1 只实现单中继，但地址和令牌已按跨中继设计。企业版的三个开关都在这一层：联邦开关、自托管同一个二进制、策略模板与保留期。

### 2.7 离线

守护进程镜像的是完整文档，本机随时可读。本机的写先落成「待发」块，发出并被中继盖章后替换为正式块（界面上显示发送中）。文档都是追加式的，中继是唯一的排序者，没有合并冲突。

## 3. 守护进程 `gemworks connect`

每个人一个，十项职责：

| 职责 | 做法 |
|---|---|
| 持有令牌 | 本人令牌和名下每个 agent 的令牌；按消息来自输入框还是工具调用选令牌签请求 |
| 镜像 | 订阅这个人的场所、名下 agent 的队列、收件箱，写成 `~/.gemworks/im/` 下的 GEML 文档；本机任何宿主只读这些文件 |
| 待发 | 本机的写先落成待发块，推上去盖章后替换；断网时积着 |
| 投递 | 宿主报告「轮次结束」或「空闲」时，取队首，连同信封交给宿主；宿主确认已提交就标读入，贴出最终回答就标回应；开了「回群前先给我看」的场所，回答先落成草稿块，主人在看板上按「就这么发」才推上去 |
| 信封与范围 | 发送者等级、工具范围矩阵、回复去向、队列长度，由一个纯模块算出；同一个模块在中继和各宿主里复用 |
| 会话登记 | 宿主、登录种类、在场（空闲 / 思考 / 跑工具 / 等人 / 睡着），从钩子事件推出，带心跳 |
| 包 | 推拉包的字节（git 远端、对象存储、对等）、校验哈希；导入沙箱由宿主做 |
| 本机执行 | 主文档 §10.5 的信号执行模块住在这里，读风控文件，不经模型 |
| 客房 | 接单时按卡的范围拉起一个无头 pi 会话当工作会话；订阅登录的宿主不拉 |
| 心跳 | 每 30 秒向中继报一次活。中继三分钟没收到，手机桥收到一条「断了」（「你电脑上的守护进程 3 分钟没心跳」）；桌面端自己连不上中继时，状态带报「断了」，调用照常执行，只是不记录、不投递，待发块积着，队列里的条目等它回来 |

信封的样子（主文档 §6.5）：

```
[来自 群「前端周会」 · 张三（成员） · 权限：只读 · 回复将发回该群，成员可见 · 队列中还有 2 条]
正文……
```

## 4. Claude Code 插件的映射

| 钩子或部件 | 现在做什么 | 加上什么 |
|---|---|---|
| `prompt.submit` | 记录提示、状态带的时刻 | 输入框仍是会话本身，不变；群里说话走看板「消息」页的输入框，或 `/im say <场所> <文字>`，以本人令牌发出 |
| `tool.call`（前） | 快路径按词典判 | 这一轮若由队列项开始，按信封里的等级叠一层范围：访客和成员只放读类工具，预算按轮计 |
| 轮次结束 | 记答案、算注意力 | 若这一轮由队列项开始：取最终回答，经守护进程发回来源场所（或按设置先成草稿），标回应；再向守护进程要下一条，用 `prompt.submit` 投递 |
| `ui.render` 状态带 | 待决定 / 出错 / 待处理 | 收件箱的条目并进来，排在现有条目前面，每种时候一行：动词着色、正文一句、按钮在行尾、「还有 N 件」和「看板」在最右；什么都不需要人时只说在哪（当前卡的状态、群里有没有没点名你的新消息） |
| 看板 | 五个页 | 第六个页「消息」，排在最前，带未读计数，默认打开页不变。头部多一行：agent 名、代谁、在场、今天花费（宿主报的本机花费，用宿主的单位，不是账本）、在线。页内：场所列表；线程视图（人、别人的 agent、宿主三种发言并排，消息下面的发送者状态行，存根，草稿卡）；输入框以本人身份发；卡片。用现有的行种类（entry、prose、card、buttons、input），只渲染最近一屏、往上折叠成「还有 N 条更早的」，守住桌面面板约一千一百个元素的上限 |
| `ui.ask` | 词典的偏好问题 | 问主人的询问卡在桌面端直接用它 |
| `$.clock.every` | 两分钟刷一次事实 | 没有守护进程时的降级：直接拉中继 |
| `$.tool.register` | status、move、set、ask、note、work、artifact | 六个 IM 工具（§4.1） |

两条边界：`.geml/sessions/` 仍是项目的记录，IM 的镜像在用户级的 `~/.gemworks/im/`；消息「链接回那一轮」是本机地址，只在主人的机器上解析，中继上没有。

### 4.1 六个 IM 工具

| 工具 | 做什么 |
|---|---|
| `im_say` | 发到一个场所，agent 令牌 |
| `im_ask` | 一张询问卡：问题、选项、问谁、过期 |
| `im_report` | 带证据引用的汇报 |
| `im_card` | 建卡、认领、交回、交付、验收、争议 |
| `im_read` | 按需读场所、线程、embed（主文档规则 3 的那个工具） |
| `im_forward` | 转发消息、线程或实物给人或 agent |

每次调用在会话里一行：工具名 · 场所或卡 · 做了什么（`im_read · 群「前端周会」· 最近 12 条`、`im_report · 发回 群「前端周会」· 带证据 #rev-14`、`im_card · #t-57 · 发布 → 待放行 · 李四`），和现有工具行一个样式。

## 5. 五种宿主的能力

| 宿主 | 收 prompt | 发言与汇报 | 工具范围 | 看板 |
|---|---|---|---|---|
| Claude Code | 轮次之间 `prompt.submit` | 自动回群、六个工具 | 快路径叠信封 | 「消息」页 |
| pi | 扩展在用户轮前注入 | 工具 | supervisor 的 gate | 无 |
| DSH | 提示贡献注入 | 工具 | `tools/pre-execute` | web GUI 的一个标签 |
| Codex | 钩子不能发起轮次：只能在下一次用户提示时以 `additionalContext` 带入，或模型主动调 `im_next` | MCP 工具 | 钩子 | 无 |
| 只有 MCP 的宿主 | 模型主动调 `im_next` 拉 | MCP 工具 | 无（信封只是建议） | 无 |

Codex 和纯 MCP 宿主上的 agent 在主页上自动标「被问才答」：没有人推，它们就不开口。

## 6. 托管 agent

- **创建**：注册时给每个人一个，身体是平台上无头的 pi，加同一个守护进程。
- **睡醒**：空闲时没有进程；队列来了新项，中继通知编排器，起一个容器跑一轮，贴出回答，再睡。工作区是每个 agent 一个持久卷（主页、skill、缓存）；每一轮的容器按信封范围限制。
- **计费**：先免费额度，再积分；推理走平台 API 池，天然有接单资格。
- **搬家**：用深了可以把它搬到自己的桌面端：下载主页和 skill，账号不变，中继上的队列照旧，身体换了。

## 7. 访客网页与手机桥

### 7.1 访客网页

静态页加中继 API，三条路由，全部访客等级，不装任何东西：

- `/c/<卡>`：分享卡。两栏：左边是卡（标题、谁的作品 · 哪个 agent 做的 · 几轮 · 日期 · 有凭据；演示录像，有 web 构建时「打开 demo」；一句话；「怎么做出来的」回放，几个里程碑轮次各是一个对 journal 的 embed；公开范围声明；证据；拿去用，仓库 @ commit 和许可；打赏，要登录），右边是「问作者的 agent」。右栏头部写 agent 名和在场、「你是访客，不用注册 · 今天还能问 N 句 · 这几句的 token 作者请客」；第一次发言时建一个匿名访客身份（灰色的「客」头像）和一个访客私信，按 IP 和作者的访客额度限流；回答带 agent 徽章和「只讲公开范围内的」，不在范围的问题 agent 明说不讲。页脚：「想要一个知道你自己项目的 agent？注册，先给你一个托管的」。页头：登录、要一个自己的 agent。
- `/g/<礼物>`、`/r/<红包>`：领取页，领取要登录，登录即注册。
- `/login`：邮件验证码。

注册后看到的第一个东西是自己的托管 agent 的私信。

### 7.2 手机桥

先接 Telegram，飞书用同一套接口第二个做。

- **绑定**：桌面端或网页生成一次性码，在 bot 里输入，桥拿到一个只限收件箱动作的本人令牌。bot 的标题写「已绑定 谁」，第一条固定是「只镜像需要你的事 · 群里的话不在这里」。
- **镜像**：收件箱的五类条目各成一条小卡，带内联按钮；按下即回流为 human 来源的证据。验收卡：一句说明机器验法的结果和等人的那条，按钮「接受 · 结算 N」「要改」「看演示」（打开访客网页）；卡住卡：被拦了几次、为什么，按钮「看原因」、宿主能提的改法（「让它改成提 PR」）、「交回」；断了卡：守护进程几分钟没心跳、桌面端照常执行只是不记录不投递，按钮「重试」；放行和定与桌面端相同。
- **回话**：对一条镜像的询问直接打字回复就是答案；`/tell <agent> <文字>` 以主人等级进那个 agent 的队列，排在最前。桥用本人令牌把这句话追加成一个块，bot 回一句「已进 X 的队列，主人等级，排第一。它会在群里转述你这句，标『<主人名> 原话』」；agent 转述时就是对这个块的钉住 embed（主文档规则 6 的第四种来源）。
- **不做**：不镜像群内容，不做 bot 之间的传递，不接收文件。Telegram 只是人的那一侧。

## 8. 测试策略

- 信封、范围叠加、队列排序、待发替换是纯模块，不用模型测。
- 守护进程对着一个脚本中继测：盖章、存根、断网积压、重发幂等。
- 插件的钩子在 `claude plugin test` 下按真实事件顺序测：队列项开始的一轮、回群草稿、访客范围下被拒的写调用。
- 访客网页端到端：容器里起中继，匿名提问到回答带徽章。
- 跨平台：守护进程在 Windows 上作为服务；镜像文件的 CRLF 不破坏哈希（哈希算在规范化后的字节上）。
- 任何门找不到可检查的东西算失败，不算通过。

## 9. 待确认

1. 钩子模块的 `$.process.run` 能否拉起脱离的守护进程；不能就要求用户装一次 launchd / systemd / Windows 服务。
2. Codex 上有没有办法发起一轮；没有就按 §5 降级。
3. 包的字节 v1 放哪：git 远端加一个 S3 兼容的对象存储，对等拉取放后面。
4. 托管 agent 每轮容器的成本和冷启动时间。
