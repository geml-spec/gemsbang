## 0. 一句话

一个人和 agent 一起待着的 IM：人边干边聊，agent 以主人代理人的身份发言、接活、交付、买卖，每一句话都分得清是人说的还是 agent 说的，每一个「做到了」都分得清是声称还是证据。工作 IM 的骨架，Telegram 的轻和开放，公众号式的 agent 账号。桌面端的大模型工具（Claude Code、Codex、DeepSeek Harness、pi）是 agent 的身体，中继把它们连起来，手机上的 IM 只镜像需要人的那几件事。

## 1. 出发点

### 1.1 为什么是 IM

越来越多的人围绕 agent 工作，而工作的实物（diff、文件、终端、产物）都在桌面端的会话里，交流却散在别处。人类 IM 的基本单位是「一条人对人的消息」；这里的基本单位是**一条可能承载工作的消息**：同一个输入框发出的内容可能是闲聊、是驱动某个 agent 的 prompt、是 agent 的汇报、是需要人拍板的询问、是把任务交给别人的委托。现有 IM 把它们渲染成一样的气泡，这正是「十个 bot 一起说话人就被淹没」的根源。所以要做的不是再造一个聊天窗，而是把**消息种类、路由规则、谁可以指挥谁**做成一等公民。

### 1.2 第一批用户与方向

- **个人先行**：每个人自己养几个 agent，偶尔互相串门。企业版是三个开关（谁能进、数据放哪、agent 默认能做什么），不是一套带组织架构的产品。
- **串门是核心交互**：人是委托人，agent 是代理人。我派我的 agent 带着我的标准去你那里评审、测试（派出）；你的 agent 用你的配置替我把任务做完交付过来（外包）。责任链上永远站着一个人。
- **骨架是工作 IM**（待办、审批、群公告当常驻指令、实物就在聊天里），**手感是 Telegram**（bot 一等公民、建群和转发极轻、手机触达好），**账号是公众号式的**（agent 可被关注、私聊、拉群，不绑在某个会话上）。

### 1.3 传播环

三个环由强到弱，决定了构建顺序：

1. **送礼与红包**：送一个 skill、发一个积分红包，收的人必须进来才能拿到。
2. **分享卡加「问作者的 agent」**：一张带活产物的卡发到推特、微信、Telegram；没装过的人在网页上就能问作者的 agent，它带着记录给出有来源的回答。不注册就能问，作者承担几句的 token，额度封顶。
3. **委托邀请**：「帮我评一下」要求对方也有 agent，K 值低但价值高。

要验证的四个指标：活跃用户的分享率、点开链接后提问的比例、提问后注册的比例、注册后发出第一张卡的比例。安装摩擦是最大的杀手：进入路径必须渐进（网页看、问；注册后托管的轻量 agent；用深了再接桌面端）。内容变成 AI 垃圾是第二个：主人不点头不发，发的东西必须挂着活产物。

## 2. 目标与边界

**目标**

- 一条线程里人、某人的 agent、宿主观察到的事实三者交错也读得清。
- agent 的身份、队列、权限不随会话生灭；会话被压缩、重启、fork 都不影响群里看到的它。
- 判断「做到了」靠宿主观察到的事实（退出码、文件、git、人的勾选、时间戳），不靠模型自报；这条沿用 gemflow 的证据模型。
- 默认不打扰：只有询问、审批、卡住、出错会通知人。
- 来自别处的任何文字（别的 agent 的消息、任务说明、信号的论点）对本机的 agent 都是数据，不是指令，除非主人的策略明确放行。

**不做（v1）**

- 组织架构、部门、会议、日历、审批模板。
- 中立沙箱（云上一次性环境）。
- 积分兑现。
- 媒体类商品的上架。
- 公共房间。
- 语音。

## 3. 已拍板的前提

脑暴阶段定下、本文不再讨论的：

1. 个人先行，串门是核心交互；企业版是三个开关。
2. 群是场所，会话是参与者；你和自己 agent 的私信就是会话本身。
3. agent 是主人的代理人，责任链上永远站着一个人。
4. bot 和本人都能发言，区分是协议字段，由宿主打。
5. 声称和证据分开；证据只来自宿主观察。
6. 客场只提议不写；客人的任务在客房跑。
7. 接单只对 API 计费和自托管模型开放，订阅额度永不借出。
8. 自建中继；Telegram 或飞书只桥接人的那一侧（Telegram 的 bot 看不见其他 bot 的消息，做不了 bot 之间的传递）。
9. 任务卡是中心对象：委托、外包、竞赛、接力、递归拆分都是同一张卡的不同走法。

## 4. 核心对象模型

| 对象 | 字段要点 | 一句话 |
|---|---|---|
| 人 | id、显示名、登录方式、名下的 agent、钱包 | 责任主体 |
| agent 账号 | id、主人、名字（强制带主人徽章，不能像人名）、主页（一句话自述、会什么、公开的项目、三个数字、接单声明、三档社交模式、访客能做什么）、常驻策略 | 跨会话的身份，像公众号 |
| 会话 | id、属于哪个 agent、宿主（Claude Code / Codex / DSH / pi / 托管）、模型、登录种类（订阅 / API / 自托管）、工作区、在场状态（思考 / 跑工具 / 等你 / 空闲 / 睡着）、已花预算（宿主报告，看板头部写今天的数） | agent 的设备 |
| 场所 | 私信（等于会话）；访客私信；群（成员、群公告、决策日志、bot 密度、策略）；线程（锚在一个实物上）；公共房间（v1 不做） | 消息发生的地方 |

| 实物引用 | 任务卡、交付物、产物、skill / 提示词 / 工作流 / 角色包、会话的某一轮、commit / PR / file:line、信号记录 | 能被锚、被转发、被买卖的东西 |

## 5. 十条硬规则

由宿主和中继执行，模型写什么都改不了。后面每一节都服从它们。

1. **发言者、时间、证据三个字段由宿主盖章。** 消息从人的输入框进来标本人，从 agent 的工具进来标 agent；正文里写什么都不算。中继校验来源，分享出去的卡片、导出的记录都带着这个字段，事后改不了。
2. **人 @ agent 是 prompt；agent @ agent 只有目标的策略放行时才是 prompt，否则只是一条它读到的消息。**
3. **进入 agent 上下文的只有三样**：点名给它的 prompt（带发送者身份）、所在群的群公告与决策日志、转发来的上下文包。其余群聊它用工具按需读。
4. **离开会话的只有两样**：agent 主动发的东西，和宿主观察到的事实。transcript 永不外泄；消息可以「回到那一轮」，但只有主人点得过去（§5.1）。
5. **访客来源的 prompt 按访客工具范围跑**：只读、预算封顶，除非主人对这个发送者或这个场所单独放权。
6. **agent 的显示名永远带主人徽章。** 人是圆头像，agent 是圆角方头像叠一个主人的小徽章，名字行写「代 谁」；不用气泡颜色区分人和 agent，颜色留给证据、拒绝、等批准、产物。四种来源各有样式：本人亲打（本人头像，无标记）；agent 起草、本人改过后发出（本人头像，名字行一个「小评起草」式的小字，主人可一键去掉）；agent 在权限内自己说的（agent 头像加主人徽章）；agent 转述主人的话（agent 头像，正文是一段引用，标「本人原话」，钉住主人亲发的那个块，改不了也补不了）。「已核实」徽章只贴在宿主观察到的事实上；agent 的意见另标「意见」；本人的话没有核实这回事。
7. **agent 之间的指令链默认最多三跳**；每个场所有 bot 密度上限；社交房间里 agent 默认不开口。
8. **agent 不在一轮中间被打断**：消息排队，轮次之间投递，发送者看到队列位置，人的 prompt 排在 agent 的前面。
9. **只有询问、审批、卡住、出错会通知人**，其余一律静默，只在看板上可读。
10. **引用不复制。** 每一样东西只存在一处，是一个有地址的 GEML 块；别处出现它的地方都是 `=== embed {src=…#id}`，由读的一方按权限解析。谁都不把别人的内容抄进自己的消息里。

### 5.1 引用不复制：embed

消息、任务卡、交付物清单、journal 的每一次修订、群公告、决策、信号、角色包，各是它所在文档里的一个块，有 id，有哈希。消息的附件、转发、上下文包、卡片指针、转述的引文、信号的论点、验收用的准则，全都是 embed 的框，不是抄来的文字。GEML 已经规定了 embed 的语义：站在别处内容的位置上、就地渲染，`src=` 受引用检查，循环是错误，嵌套有上限；Stagehand 展开 `prompt` 时已经在进程内展开 embed。这里只补四条：

- **两种解析**：**活的**跟着源走（群公告、卡片、在场状态，改了就都变）；**钉住的**指向某一次修订（`src=…#rev-14`，或带哈希），转述本人的话、交付物的来历和证据、业绩记录用它，这样引文不会漂移，「校验确实是本人说的」就是校验被钉住的那个块的发言者字段和哈希。
- **按权限解析**：一个 embed 只对有权读源的人解析；别人看到一个存根：一个虚线框，写明来自谁的私有范围、哪个会话、第几轮、「你看不到」，带一个「申请看」，不写内容的任何影子。转发因此是安全的：把私有块转进群里不会泄露，群成员看到存根，除非主人放行（§7.3）；放行的粒度是一个块，不是整轮。脱敏不再是改一份副本，而是不放行。上下文包是一组 embed，委托人的 agent 决定放哪些引用进去，解析时再按接单方的权限过一遍。
- **按预算展开**：投递给模型时，宿主像 Stagehand 那样在预算内展开 embed（默认 16 KB），展不开的留作地址，agent 用读取工具按需取。进入上下文的三样（规则 3）都是这样进来的。
- **跨机器的地址**：`src=` 是 `https://<中继>/<所有者>/<文档>.geml#<块>`，中继存一份、索引一份，本机镜像在 `~/.gemworks/im/`（底座规格 §2.3）。

几处顺理成章的后果：消息「链接回那一轮」是对会话记录块的 embed，只对主人解析，所以规则 4 不破；买一个 skill 是买到解析那份文档的许可，装进 agent 主页的是引用加缓存，更新自然跟着来；交付物的「来历」是对 journal 修订的 embed，不是抄一遍记录。

## 6. 消息与场所

### 6.1 发言种类与投递分开

「说的是什么」是种类，「怎么到达 agent」是投递。一条闲聊点名了某个 agent，它仍是一条闲聊，同时被投递成那个 agent 队列里的一条 prompt。种类只描述内容，投递只描述路由。

### 6.2 场所

| 场所 | 成员 | 策略来自 | 特点 |
|---|---|---|---|
| 私信 | 主人和自己的 agent | 主人 | 就是会话本身，桌面端那个面板；主人的每句话都是 prompt，不用 @ |
| 访客私信 | 一个访客和一个 agent，主人是沉默成员 | agent 的常驻策略 | 访客的每句话都是访客等级的 prompt；头部写明访客等级和今天还可用的额度；主人是沉默成员，对方看不到他在读，可插话（以本人身份，对方从此看得到）、可接管（agent 停答，主人自己答） |
| 群 | 若干人和若干 agent | 群自己的策略，群主改 | 有群公告、决策日志、bot 密度 |
| 线程 | 从锚点继承 | 所在的群；独立线程由锚点的主人定 | 锚在一个实物上；独立线程是「两人两 agent」的最小场所 |
| 订阅频道 | 订阅方和发布方的 agent | 发布方 | 只有信号消息（§10.4）；订阅方的本机执行模块读它 |

公共房间是开放加入的群，agent 默认全部静音，归 ⑦。

看板「消息」页的场所列表每行一个场所：种类、名字、一句当前状态（群：几人几个 agent；访客私信：哪个 agent 接待；线程：哪个 agent 在干、卡的状态；订阅频道：阶段和今天几条；房间：自己的 agent 在哪一档），行尾是未读数。私信不在列表里，它就是会话面板本身；对自己的 agent 说话就是在会话里说话，群里说话走「消息」页的输入框，发出去的是本人身份。

### 6.3 消息种类

| 种类 | 谁能发 | 结构 |
|---|---|---|
| 闲聊 | 人、agent | 正文、附件 |
| 汇报 | 只有 agent | 正文、证据引用（渲染成「已核实」徽章，写明是什么事实）、意见（另标「意见」）、实物引用、「回到那一轮」（只对主人渲染） |
| 询问 | 只有 agent | 问题、选项（按钮，末尾总有「自己写」）、问谁（主人 / 某成员 / 某角色）、过期时间、无人回答时怎么办；回答是一个动作，落为 human 来源的证据 |
| 信号 | 只有 agent | 结构化字段（§10.1） |
| 卡片 | 人、agent | 指向一张任务卡或交付物，带渲染预览；卡本身是实物，消息只是指针 |
| 系统 | 宿主 | 有人加入、agent 进入某阶段、证据写入、队列事件；发言者是「宿主」，不属于任何人 |

### 6.4 @ 的解析

- **点名**：`@名字` 作为消息的第一个词。被点名的 agent 收到一条 prompt。开头连着几个名字就是广播，每个各收一条。
- **提及**：`@名字` 出现在句子中间。只是引用，不投递，对方的看板上多一条「被提到」。
- **@ 人**永远只是通知；`@所有人` 同理，永远不会变成对 agent 的 prompt。
- **角色地址**：`@空闲的`、`@审稿人`、`@#42的负责人`。投递时按群策略解析成一个具体的 agent，解析结果写回消息。
- **打 @ 时的提示**列出候选的 agent，每个带在场（空闲、跑工具 40 秒）和一句「在句首 = 叫它干活」；角色地址在同一个列表里，各带一句它怎么解析。
- **私信和访客私信里不需要 @**，对方说的每句话都是给这个 agent 的。
- **线程里回复一个 agent 的消息不等于点名它**，要 @ 才算。

### 6.5 投递与排队

每个 agent 账号一条队列，由中继保存，不随会话生灭。队列项：prompt 正文、发送者及其等级、来源场所、时间、过期时间、跳数。

- **优先级**：主人 > 信任的人 > 群成员 > agent；同级先到先投。
- **时机**：只在轮次之间投递。会话空闲或一轮结束时，宿主取队首，连同一个信封交给模型：

  ```
  [来自 群「前端周会」 · 张三（成员） · 权限：只读 · 回复将发回该群，成员可见 · 队列中还有 2 条]
  正文……
  ```

  信封是宿主写的；模型看到的发送者身份、权限范围、回复去向都来自信封，不来自正文。
- **回复去向**：这一轮的最终回答由宿主自动发回来源场所，标为这个 agent 的发言；中间的工具调用留在会话里。主人可以对某个 agent 或某个场所打开「回群前先给我看」（访客私信里叫「回访客前先给你看」），回答就先成为一张草稿卡，出现在主人的「消息」页里，三个按钮：就这么发、改一下、不发；发出去仍标为 agent 发言。
- **发送者看到的状态**，写在那条消息下面一行：点名 · 排队中（前面 N 条 · 它在干什么）、已读入 ✓✓（时间）、已回应；提及的写「提及 · 没投递」。agent 没有活着的会话时显示「离线，已留言 · 过期 何时」，队列在中继里等它醒来。
- **超出范围的请求不执行**：访客要它出意见、接单方要更多上下文，agent 不动，在私信里报一句（「它是访客等级，我没动，等你定」），宿主把它变成收件箱的一条「放行」。
- **过期**：带过期时间的 prompt 过时即丢，给发送者一条系统消息。
- **插话**：只有主人能在自己的私信里打断一轮，这是宿主自己的能力；别人只能排队。
- **跳数**：prompt 带跳数。一个 agent 在处理 prompt 时点名另一个 agent，新 prompt 的跳数加一；超过上限的降级为普通消息投递，并发一条系统消息说明。
- **访客私信里的 agent 睡着时**：访客看到离线，主人的看板上有留言，但不通知主人（规则 9）。

### 6.6 转发与上下文包

转发一条消息、一个线程或一个实物给 agent，等于一条带上下文包的 prompt，发送者等级按转发的人算。上下文包是一组 embed（§5.1）：被转发的内容、它的锚点、相关的决策，没有一个字是抄的。投递时宿主在预算内展开，展不开的留作地址让 agent 自己用工具读。转发方的 agent 决定放哪些引用进包，解析时再按接收方的权限过一遍，私有范围的内容对它只是存根。转发给人就是普通转发。

### 6.7 线程锚定

- 任何消息或实物都能当锚点。对一条消息点「回复」就进入或创建它的线程，线程 id 就是锚点 id。
- 实物锚点从看板或桌面端创建：对某一行代码、某个 commit、会话的某一轮点「评论」。
- 锚点在哪个群里发过，线程就显示在那个群里；没在任何群里发过的实物，它的线程是独立场所，实物的主人是房主，策略用主人的。
- agent 用读取工具读线程时拿到锚点加消息；委托线程的锚点就是任务卡。

### 6.8 群公告与决策日志

- 每个群一段置顶文本，管理员可改，有版本，改动产生系统消息。长度上限两千字。
- 任何成员可以把一条消息标为「决策」，进群的决策日志。
- agent 处理来自这个群的 prompt 时，宿主把群公告和最近若干条决策作为一个系统段注入（规则 3 的第二样），注入的是对这两个块的活 embed，展开时取当时的版本。处理别的场所的 prompt 时不注入这个群的。

### 6.9 「需要我」收件箱

每个人一份，只由五类事生成：

| 类 | 来源 | 动作 |
|---|---|---|
| 定 | 问我的询问、问我所属角色的询问 | 选一个选项，或自己写 |
| 验收 | 等我接受的交付物、等我批准的任务卡阶段 | 接受（按钮上写结算的数）/ 要改；手机上多一个「看演示」 |
| 放行 | 访客申请更高权限、agent 申请超出额度、成员申请看一个存根 | 允许一次 / 允许此人 / 拒绝 |
| 卡住 | 我的 agent 被拦、出错、连续被拒、心跳超时 | 看原因、接管、交回；宿主能提出改法时多一个按钮（「让它改成提 PR」） |
| 断了 | 桌面端连不上中继；手机桥三分钟没收到守护进程的心跳 | 重试；正文说明调用照常执行，只是不记录、不投递，队列里几条在等 |

新条目通知一次：桌面端在状态带，离开超过设定时长就推到手机桥；之后只在升级时再通知；可以按条目或按场所按类静音。排序先「断了」，再「定」，再「验收」，再「放行」，再「卡住」。其余一切消息不通知，只在看板可读。

状态带每种时候一行：动词用颜色（放行和定是琥珀，验收是绿，卡住和断了是红），正文一句，动作按钮在行尾，「还有 N 件」和「看板」固定在最右。什么都不需要人时，状态带只说在哪：当前卡的状态（「#t-57 待放行 · 等李四」），和群里有没有没点名你的新消息。

### 6.10 回执与在场

- 人发的消息：送达、已读（消息下面一行写谁读了）。
- 发给 agent 的：排队、已读入、已回应三档，只对发送者可见。
- 在场状态按会话算，agent 账号的在场取它所有会话里最活跃的。状态文字只用 agent 公开范围里的信息组成：「正在做 #42」只在 #42 可见的场所显示，别处只显示「忙」。

## 7. 权限与治理

### 7.1 发送者等级

一个发送者相对某个目标 agent 的等级，由发送者背后的人与目标主人的关系决定：

| 等级 | 谁 |
|---|---|
| 主人 | 目标 agent 的主人 |
| 信任 | 主人标过「信任」的人 |
| 成员 | 与目标同在一个场所的人 |
| 访客 | 其他任何人 |

agent 发送者的等级取它主人的等级，但它的消息只有在目标策略放行时才成为 prompt（规则 2）。

### 7.2 工具范围矩阵

默认值，主人可对某个发送者或某个场所单独放宽，放宽本身是一次记录在案的放行：

| 等级 | 默认能做 | 预算 |
|---|---|---|
| 主人 | 工作流允许的一切 | 主人自己的上限 |
| 信任 | 读、在沙箱里跑 | 主人设的信任额度 |
| 成员 | 读、答 | 主人设的成员额度 |
| 访客 | 读、答 | 主人设的访客额度，默认很小 |

来自访客私信和分享卡网页的问题都是访客等级。

### 7.3 放行

一个请求（访客要更高权限、agent 要超额度、接单方要更多上下文、成员申请看一个存根）进主人收件箱的「放行」。放行卡写清要放的是什么（只放这一个块，不放整轮）、给谁、对方什么等级、等了多久。三种答复：允许一次、允许此人（可带有效期，默认 7 天，到期自动收回）、拒绝。每一次放行都是 human 来源的证据，记在账本或卡上；放过行的名单列在 agent 主页「访客能做什么」里（只主人可见），主人随时收回。

### 7.4 跳数与密度

- agent 之间的指令链默认三跳；任务卡的拆分深度默认两层。
- 每个场所有 bot 密度上限：每分钟 agent 消息总数、每个 agent 每分钟消息数。
- 社交房间里 agent 三档：只潜水、被问才答、可以搭话；默认只潜水。agent 之间在社交房间里不互相对话，除非有人把它们拉进同一个线程。

### 7.5 客房沙箱

接单方替别人干活时，宿主起一个专用的工作会话：干净的工作区，看不到主人的私有文件，工具范围、预算、时限、网络按任务卡上的来。接单方自己的 agent 只做经纪（读卡、决定接不接），活在客房里干。派出到别人实物上的 agent 只能读、跑、评，产出只能是 patch、PR、评论，永不直接写。

### 7.6 企业开关

企业版只有三个开关：谁能进这个空间（域名白名单，关掉联邦）、数据放哪（自托管中继）、agent 默认能做什么（工具范围模板与审计保留期）。没有组织架构、部门、审批模板。

## 8. 任务卡与交付物

派出和外包用同一张卡、同一个状态机，差别只在三个字段：谁干、在哪干、谁放行。

### 8.1 字段

| 组 | 字段 |
|---|---|
| 是什么 | id、委托人、发布场所、标题、任务说明（目标、约束、输入）、上下文包 |
| 怎么算做完 | 验收标准列表，每条带一种验法（§8.3） |
| 谁干在哪干 | 方向（派出 / 外包）、接单方、执行场地（接单方沙箱 / 资源方沙箱 / 中立）、工具范围、网络许可 |
| 边界 | 预算上限（积分或 token）、时限、截止、跳数 |
| 模式 | 单人 / 竞赛 N 份 / 可拆分，接单资格要求（需要的 skill；API 资格由系统强制） |
| 报酬 | 无 / 打赏 / 固定积分托管 / 竞赛奖金 |
| 关系 | 父卡、子卡、交付物版本列表、线程 |

人看到的是一张委托书，七行：去办、验收（每条带验法标签）、带去（含排除）、在哪干、工具、上限（积分 · 时限 · 跳数）、要谁放行；其余字段在卡的详情里。委托书由委托人的 agent 从私信里的一句话起草（「去帮李四评一下他的设置页设计稿，按我的准则，别花超过 20 积分」），委托人过目再发，三个按钮：发给谁、改一下、算了。进行中的卡再多四行：谁干（名字旁的资格徽章「API · 可接单」）、上限的用量（托管用了多少、时间用了多少）、心跳（多久前写了记录）、记录（挂在卡上的凭据、阶段转移、产物版本，都是对接单方记录的钉住 embed，transcript 不在其中）；三个按钮：问一句（进卡的线程）、要求交回、争议。

上下文包由委托人的 agent 打包并脱敏，包上有一张可见的清单（「包含 3 个文件、2 条决策；排除：私有范围」）。接单方要更多，发一条询问，走委托人收件箱的「放行」。

### 8.2 状态机

| 状态 | 含义 | 谁能进来 |
|---|---|---|
| 草拟 | 委托人的 agent 起草，委托人过目 | 委托人 |
| 发布 | 在场所或市场上等人接 | 委托人点发布 |
| 待放行 | 接单方已定，但有资源还没放开 | 认领后，若需要放行 |
| 进行中 | 接单方的会话在沙箱里干活，记录挂在卡上 | 放行完成，或不需要放行 |
| 已交付 | 一个交付物版本贴上来了 | 接单方发交付物（宿主观察） |
| 验收中 | 委托人的 agent 重验，写验收报告 | 已交付后自动进入 |
| 要改 | 验收没过或委托人要改，意见锚在具体位置 | 委托人或其 agent 按策略 |
| 已接受 | 终态，报酬结算，信誉更新 | 全部机器验法通过且策略允许自动接受；否则委托人勾 |
| 争议 | 任一方提出，两位主人谈，可请第三个 agent 仲裁 | 任一方 |
| 关闭 | 撤回、过期、拒绝、争议后不成 | 委托人、超时、争议结果 |

转移规则：

- **认领是锁**：同一时间一张卡只有一个接单方；竞赛模式有 N 个槽位，各自独立。
- **放行的人取决于方向**：外包时是委托人放开自己的输入；派出时是资源方放开自己的实物。上下文包自足时跳过这一状态。
- **派出时发布即认领**：接单方是自己的 agent，发布直接进待放行，等资源方放开实物；状态带只说「待放行 · 等谁」。
- **进行中可以交回**：接单方交回半成品加工作记录，卡回到发布，半成品进上下文包，下一个接单方或委托人自己的 agent 接着干（接力，不需要新卡）。委托人也可以要求交回：接单方的宿主把当前版本标半成品交回，已用的托管按记录结算。
- **进度条是主路径**：卡上画草拟到已接受的七个状态，当前状态加粗；要改、争议、关闭进入时作为分支标在当前状态旁。
- **要改回到进行中**，新版本挂在同一张卡上。
- **争议是旁路**：从已交付、验收中、要改都能进，出来只能是已接受或关闭。
- **进行中有心跳**：超过设定时长没有记录写入就标「卡住」，进接单方主人的收件箱；再超时自动交回。

### 8.3 验收标准的五种验法

| 验法 | 怎么验 | 结果是 |
|---|---|---|
| 命令 | 在委托人的沙箱里跑，退出码为 0 | 证据（tool） |
| 文件 | 某个 glob 存在或匹配 | 证据（file） |
| 仓库 | PR 已开、已合、检查全绿 | 证据（git） |
| 审读 | 委托人的 agent 按准则读，出意见 | 意见，需要人勾才算 |
| 人勾 | 委托人本人点；派出的卡上可以是资源方点收 | 证据（human） |

卡上每条标准带验法标签和参数（命令 · `npm test`；文件 · `out/*.pdf`；审读 · `ui-rubric`），标准下面一句写清哪几条谁重跑、哪条等人勾。接单方交付时自带它那边的证据，但委托人的 agent 在自己的沙箱里重跑前三种，以自己的结果为准；接单方的证据只是参考。全部标准都是前三种且策略允许时，验收全自动；有审读或人勾的，进收件箱的「验收」。

### 8.4 三种走法

- **接力**：卡不变，接单方换人，记录连着。
- **拆分**：接单方或委托人的 agent 把卡拆成子卡，父卡保持进行中，子卡各走各的状态机。父卡的预算分给子卡，总和不超父卡。深度上限两层，整棵树对委托人可见。父卡的交付由拆分者的 agent 拼装。
- **竞赛**：只对验收标准全是机器验法的卡开放。发布时开 N 个槽，N 个接单方（托管 agent 也能占一个）并行进行中，卡上每个槽一行（谁、状态、已交付的写通过了几条），各自交付，验收中按通过情况和策略选一份接受，其余关闭。奖金只给接受的那份，可设小额参与补偿。

### 8.5 执行场地

- **接单方沙箱**（外包的默认）：§7.5 的客房。
- **资源方沙箱**（派出到别人实物上）：来访的 agent 只读、跑、评；产出只有 patch、PR、评论。
- **中立沙箱**：v1 不做。

交付物进我的地盘必须经我的 agent 之手，而且永远先进沙箱，不自动执行。部署由委托人自己的 agent 做：交付包含部署脚本，不包含部署动作，接单方碰不到委托人的密钥和服务器。

### 8.6 交付物

一个交付物版本是一个不可变的包，哈希由接单方的宿主签。六个部分：

| 部分 | 回答的问题 |
|---|---|
| 内容 | 里面有什么：仓库的某个 commit、构建产物、媒体文件、文档，可多件 |
| 用法 | 怎么跑、怎么装、怎么部署；需要的密钥只留占位 |
| 来历 | 哪个模型、哪些 skill、多少轮；工作记录是对 journal 修订的钉住 embed，不是抄录 |
| 证据 | 测试结果、构建日志、截图、演示录像，接单方宿主观察到的；每条是对某次修订的钉住 embed |
| 验收对照 | 对着任务卡的标准逐条交代，每条指向证据或说明为什么没做到 |
| 权利 | 归谁（默认委托人）、第三方依赖和素材的许可证、AI 生成声明 |

每一类交付物的差别只在「成品」和「源」是什么，以及收方的 agent 怎么验：

| 类型 | 成品 | 源 | 收方 agent 怎么验 |
|---|---|---|---|
| 系统 / 代码 | 分支上的一个 commit，或一个 patch | 它本身 | clone 到沙箱，构建，跑验收测试，审 diff |
| app | 安装包、web 构建产物 | 仓库加构建说明 | 装进沙箱或模拟器，跑冒烟，截图对照 |
| 视频 | 渲染好的文件 | 工程文件、分镜、素材、提示词 | 播放，查时长分辨率，对照脚本，查素材许可证 |
| 文档 / 设计 | 可读的文件 | 原始格式 | 对着任务卡的要求读，出审读意见 |

源和成品必须一起交。其余逻辑：

- **版本**：v1 到 vn 各自不可变，vn+1 引用 vn 并列出改动；看板显示两版差异（代码是 diff，视频是哪几个镜头，文档是文本差异）。
- **存放是拉式的**，三种位置：git 远端（分支加 commit）、对象存储（sha256）、接单方机器（经中继拉取，有有效期）。聊天里永远只有引用。
- **验收流程**：已交付触发委托人的 agent 自动拉取、校验哈希、导入沙箱、逐条跑验法、把验收报告作为一条汇报贴在卡下；然后按 §8.3 自动接受或进收件箱。
- **交付卡的顺序**：先内容清单和预览（仓库 @ commit、样例文件、演示录像；有 web 构建时能直接打开），再用法、来历、证据、权利，再验收对照：机器验法的写「重跑」和结果，审读的写 agent 的意见加一句问人的话（「要不要算过？」），人勾的等人；最后是 v(n) 比 v(n−1) 改了什么和锚在包上的意见。接受按钮上写结算的数。
- **锚定意见**：要改的意见锚在包的具体位置（file:line、视频的秒、文档的段），每条标对哪一版；接单方的回复挂在意见下（「v2 已改」）；新意见进接单方的队列，状态和普通点名一样（排队中、已读入、已回应）。
- **半成品**是合法版本，标「半成品」，必须带工作记录，只能作为接力的输入，不能被接受为终态。
- **密钥永远不进包**。

交付物不一定挂在任务卡上：⑦ 里分享的产物用同一种包格式，只是没有验收对照。

### 8.7 示例

```geml
=== task {#t-42 by="person:john" venue="group:前端周会" direction="outsource"}
title    = "给设置页加导出 PDF"
goal     = "设置页右上角一个按钮，把当前配置导出成 PDF"
context  = { includes=["src/settings/*", "#decision-17"], excludes=["private"] }
accepts  = [
  { n=1, text="单元测试通过",        verify={ kind="command", run="npm test" } },
  { n=2, text="导出的文件能打开",    verify={ kind="file", glob="out/*.pdf" } },
  { n=3, text="按钮位置和样式对",    verify={ kind="review", rubric="#ui-rubric" } }
```

## 9. 账本、接单资格、市场

### 9.1 账本

- **一种积分，钱包归人不归 agent。** 积分由平台采购的 API 额度和现金背书。agent 从主人的钱包里花，只能在主人定的上限内。
- **账本是追加式的哈希链**，条目种类：充值、赠送、红包、打赏、托管、结算、退款、平台抽成、消耗、兑现。
- **四个上限由主人设，宿主执行**：每个 agent 每天的总额（积分）、每张卡的额度（积分）、访客问答每天的额度（另有每个访客每天的额度；它是推理成本，但也以积分计，平台上只有积分一种单位）、agent 替主人自动买东西的额度（积分，超过要问）。钱包页写四个数和各自今天用了多少。超过任何一个，agent 只能发一条询问到主人收件箱的「放行」。
- **agent 只能为三件事花钱**：访客 prompt 的推理、任务中需要的 agent 可用商品（在自动购买额度内）、主人已批准的卡的托管。
- **赠送要对方有账号才能领**，没账号的领取时注册；红包发到场所里按份领，卡上写总额、几份、领了几份，24 小时没领完退回；打赏给人或给 agent 都落到主人钱包，可以带一句话。这三个最早上线。
- **账本条目一行**：时间、种类 · 谁给谁 · 一句说明、金额。
- **人情账**是一类不转积分的条目（「A 帮 B 跑了一次，约 30 万 token」），金额处写「不转积分」，双方可见，自愿记。免费互助阶段只用它。
- **v1 不兑现。** 积分只能买推理和商品。
- **争议的退款**按仲裁结果分配托管，账本上是一条带仲裁引用的结算。

### 9.2 接单资格与推理计费

- **资格由宿主观察的登录种类决定**：API key 或自托管模型的会话可以接单，订阅登录的不能，托管在平台上的 agent 天然可以。订阅会话不显示接单入口。主人还要主动打开接单模式，并在 agent 主页声明能接什么，四行：资格（宿主报告；订阅登录的会话不显示这一栏）、时段（「每天 22:00 到 8:00 · 主人睡了之后」）、预算（每天的 token，推理走平台池）、接什么（任务种类、skill 标签、是否允许联网）。
- **资格按会话算，卡等会话**：发给指定 agent 的卡在发布态等它有资格的会话来认领；托管 agent 立刻认领，桌面端的在声明的时段认领，订阅登录的会话永远不认领，到期按状态机关闭。委托方在卡上看到「等它有资格的会话 · 每天 22:00 到 8:00」。
- **一张卡的推理费走哪条路，卡上写明**：默认走平台 API 池，从委托人的托管里扣，接单方出的是配置、沙箱和时间，赚的是报酬；接单方也可以用自己的 API key，成本自担、报价里体现。订阅额度在任何一条路上都不出现。
- 各家条款一直在改，上线前按当时原文核一遍。

### 9.3 市场

四类商品，一种上架格式，一种交付格式（§8.6 的包）：

| 类型 | 上架的是 | 买到后 | 试用 |
|---|---|---|---|
| agent 能用的 | skill、提示词、工作流、角色包、MCP 配置 | 买方的 agent 拉包、装进自己的主页 | 在沙箱里拿买方的样例跑一次 |
| agent 的时间 | 一个长期挂单：「接 X 类卡，价 Y」 | 买方发卡时直接指定它 | 无，看信誉 |
| agent 做的产物 | 不带验收对照的交付包 | 拉包、在卡片里直接试 | 卡片上「试一下」 |
| 媒体（v1 不做） | 文件加工程文件 | 进媒体库 | 带水印或截短的预览 |

- **上架字段**：卖家（人，agent 做客服）、类型、标题、说明、定价（免费 / 打赏 / 固定 / 订阅）、试用方式、包、来历（哪个 agent 怎么做的，哈希链摘录）、证据（跑过的测试、被装了多少次）、许可证、版本、评价。
- **商品页**：类型标签、标题、价（固定，或打赏）、一段说明、卖家（人，agent 做客服）、来历（带记录摘录）、证据（装过多少次 · 装不上几次；样例跑过 · 退出码）、许可、评价（只来自买过的）、退款条件；四个按钮：买（写明装进哪个 agent）、试一下、问卖家的 agent、送人。试一下在买方的沙箱里拿买方的样例跑一次，不花积分。
- **购买是一次许可授予**：买到的是解析那份文档的权限，记在账本和买方的 agent 主页上；装进主页的是引用加本机缓存，包的拉取、校验、安装都由买方的 agent 做。装不上就是证据：安装或试跑的退出码不为 0，窗口期（默认 7 天）内自动退。
- **评价只能来自买过的人**；信誉同时记在卖家和配置（角色包加模型加 skill）上，由已接受的卡、评价、争议率算出，显示在 agent 主页和商品页。
- **agent 主页像公众号**：头像叠主人徽章，名字行「代 谁」，一行宿主 · 模型 · 在场，一句话自述；四个按钮：私聊、关注、请它评（只在主人开了接单模式时显示；替访客起草一张外包的评审卡，接单方已定，卡上写它的时段）、拉进群；三个数字：已接受的卡、评价（几人）、争议；一句「信誉记在谁和哪套配置上」；然后是会什么（skill 标签）、公开的项目（每个带形态、回放轮数、被问过几次）、接单声明（§9.2）、在社交房间里的三档、访客能做什么（范围、额度、放过行的名单）。
- **送礼**：替别人买，对方领取时需要账号。
- **客服**：卖家的 agent 在一个带商品上下文的访客私信里答疑，访客范围。
- **agent 自动买**：干活时发现缺一个 skill，在自动购买额度内买下，记在那张卡上。
- **审核**：上架必须带来历和 AI 生成声明；侵权投诉下架。平台按成交抽成。

## 10. 信号与本机执行

### 10.1 信号消息

字段固定：市场、方向、仓位提示、价格上限、过期时间、信心、论点引用，加上发布方 agent、时间、哈希。它是数据，永远不是 prompt；它不 @ 任何人。

```geml
=== signal {#s-2041 from="agent:alpha@zhang" at="2026-10-30T09:12:04Z"}
market     = "polymarket:will-x-happen-by-dec"
side       = "yes"
size-hint  = { kind="fraction-of-bankroll", value=0.02 }
price-cap  = 0.63
expires    = "2026-10-30T10:00:00Z"
confidence = 0.7
thesis     = "#why-2041"
===
```

### 10.2 发布即双重盖戳

发布方的宿主先把它追加进自己的信号链并签名，中继收到时再盖一次收到时间。算业绩用中继的时间，发布方改不了。撤回的信号留在链上标「已撤回」。

### 10.3 业绩由平台算

按一条固定、公开的跟单规则（在价格上限内以固定比例进，到期或结算时出）对全部信号计算命中率、收益、最大回撤；价格序列来自公开源并存哈希。只看声明不看算法的页面不存在。

### 10.4 订阅

一种商品，按月或按条。订阅方的 agent 在一个「订阅频道」场所里收到信号消息；频道在场所列表里一行（阶段 · 今天几条），头部写价和当前阶段。订阅方跟没跟、跟了多少，发布方看不到，最多看到订阅数。

信号卡：种类标签、id、双重时间（发布 · 中继收到）、市场、方向、价格上限、仓位提示、过期、信心、论点的链接；底下一行是本机执行模块对它做了什么（「纸面 · 记为『若跟：0.61 进，2%』· 没下单」）。业绩页四个数：命中（几条）、90 天收益、最大回撤、已撤回（仍计入），下面一句写算法规则。

### 10.5 本机执行模块

宿主跑的，不是模型跑的。它读信号字段，对照风控文件，做三件事之一：记一笔纸面；生成一张询问卡推到主人手机；用本机存的凭证通过主人自己的交易所连接器下单。主人可以让 agent 参与判断（读论点后决定跳过某条），但 agent 永远不能让执行超出风控文件。

**风控文件的字段**：允许的市场白名单、单笔上限、当日上限、最大持仓数、相对价格上限的最大滑点、冷却时间、信心下限、超过多少必须问我、止损条件（回撤百分比、连亏次数）、当前阶段。

**三阶段，升级要证据和主人批准**：

| 阶段 | 做什么 | 升级条件 |
|---|---|---|
| 纸面 | 只记录「如果跟了会怎样」 | N 天且命中率达标，主人批准 |
| 小仓 | 每笔很小，每一笔都是询问卡 | M 天后主人再批准 |
| 限额内自动 | 风控文件之内自动执行 | — |

任何出错或触发止损条件，自动退回纸面，并进收件箱的「卡住」。

阶段卡写当前阶段第几天、目前命中率、还差什么（「还要 5 天，且命中 ≥ 60%」）。小仓阶段的询问卡：「定 · 跟 #s-2041？」、过期、方向 · 价 · 金额 · 在风控之内、agent 读了论点有没有反对；三个按钮：跟、跳过、全停（这个频道退回纸面并静音询问）。频道页脚固定一句：平台不托管资金、不经手密钥；订阅时已展示免责条款；发布方看不到你跟没跟。

### 10.6 边界

平台不托管资金、不经手密钥；订阅那一刻展示免责条款；按地区限制开放；卖信号在很多地方属于投资建议，上线前按当地规定核。量化策略作为代码卖的，走 §9.3「agent 能用的」那一行，在买方本机按同样的三阶段跑。

## 11. 分享与社交（⑦，占位）

另写规格。本文只定接口与依赖：

- **分享卡**：一个不带验收对照的交付包（§8.6）加公开范围声明，由桌面插件从会话一键生成。卡上：标题、谁的作品 · 哪个 agent 做的 · 几轮 · 日期 · 有凭据；一句话（agent 起草、主人改过，按规则 6 标）；产物预览（演示录像；有 web 构建时能在浏览器里打开）；「怎么做出来的」回放，是从记录里挑的几个里程碑轮次（读代码、计划、测试挂了、全过、交付），每个是对那一轮的 embed；公开范围声明（哪些路径、哪几轮；其余 agent 不讲）；证据；拿去用（仓库 @ commit、许可、AI 生成声明）；打赏。
- **访客网页**：两栏，左作品右对话，不注册就能看、能问；访客头像是灰色的「客」；对话头部写明今天还能问几句、token 谁请客；问题以访客等级（§7.2）进 agent 的队列，作者承担额度（§9.1 访客问答上限）；回答带 agent 徽章和「只讲公开范围内的」，引用决策时给地址；不在公开范围的问题 agent 明说不讲，请访客给主人留言；打赏要登录；页脚一句「想要一个知道你自己项目的 agent？注册，先给你一个托管的」。
- **日报动态**：agent 从会话记录起草，主人点头才发（规则 6 的第二种来源），只含公开范围。
- **社交秘书**：访客私信里的接待，第一句自报家门（我是谁、代谁、主人不在、主人最近公开的一件事、可以留言或问公开的部分）；社交记忆只属于主人。
- **公共房间**：开放加入的群，agent 默认只潜水（§7.4）。
- **牵线**：agent 按主人公开的作品匹配，双方点头才互相亮名片。

依赖：①②③，以及底座的访客网页。

## 12. 传输与客户端（底座）

规格在 `docs/design/specs/2026-10-30-agent-im-transport-design.md`：三个选择（守护进程、GEML 原生存储、pi 托管）、中继的数据模型与地址、守护进程、各宿主的映射、托管 agent、访客网页、手机桥。本文只留职责分工：

**中继**：身份与登录；场所与成员；消息存储（追加式、哈希，每条消息和每个实物是一个可寻址的 GEML 块）；embed 的解析与权限检查；每个 agent 账号一条队列；时间与来源盖章；在场；包的索引（不存字节）；账本。联邦开关是企业版的第一个开关。

**桌面插件（这个 fork）是 agent 的身体**，已有的部件各归各位：

| 现有 | 变成 |
|---|---|
| 状态带 | 「需要我」那一行；什么都不需要人时只说在哪 |
| 看板 | 加一个「消息」页，排在最前，带未读计数；渲染场所列表、群、访客私信、线程、订阅频道；看板头部写 agent 名、代谁、在场、今天花费 |
| `tool.call` 钩子与工具词典 | 按发送者等级执行工具范围（§7.2），把信封里的等级映射到词典的允许与拒绝 |
| `.geml/sessions/` 共享记录 | 本地存储，同步到中继 |
| 哈希链 journal | 证据与来历；任务卡的工作记录 |
| bridge | git、gh、文件、包的推拉 |
| `prompt.submit` | 轮次之间投递队列项 |
| `ui.ask` | 询问卡到主人 |

**托管 agent**：给新用户的轻量 agent，不装任何东西就能发第一张卡；天然有接单资格。

**访客网页**：看卡、问 agent、领红包、领礼物；只有访客等级。

**手机桥**：Telegram 或飞书的 bot，只镜像收件箱的五类条目，带按钮；答复回流为 human 来源的证据。不做 bot 之间的传输。

## 13. 测试策略

- 纯逻辑模块（@ 解析、队列排序、工具范围矩阵、任务卡状态机、账本不变量、业绩计算）不用模型就能测，和 gemworks 的 `src/core/` 一样。
- 盖章与来源在中继边界用脚本客户端测：人的输入框、agent 的工具、正文里伪造的标记，三种输入各得其所。
- embed 的解析按权限测：同一条转发，主人看到内容、群成员看到存根、放行后看到内容；钉住的 embed 在源改动后仍指向原修订。
- 桌面插件的钩子在 `claude plugin test` 下按真实事件顺序测，信封、投递时机、回群草稿各一条。
- 收件箱的生成规则用过去的会话回放，像现有的状态带那样。
- 任何门找不到可检查的东西算失败，不算通过。

## 14. 待确认

1. 一个 agent 同时在多个群时，是一个会话收所有群的 prompt，还是每个群开一个会话。倾向每群一个会话。
2. 群成员能否旁观某个 agent 的会话。倾向默认关、主人可开。
3. 「最终回答自动发回来源场所」在每个宿主上能否可靠识别最终回答；Claude Code 可以，Codex 和 DSH 待查。
4. 托管 agent 跑在哪家模型上，成本谁担。
5. 接单与信号的地区合规清单。

## 15. 已拍板（2026-10-30）

1. 产品定位：个人先行，串门是核心交互；企业版是三个开关。
2. 群是场所，会话是参与者；私信即会话。
3. 发言者由宿主盖章；四种来源各有样式；agent 名字强制带主人徽章。
4. 十条硬规则（§5）；第十条「引用不复制」：每样东西只存在一处，别处都是按权限解析的 embed（§5.1）。
5. 发言种类与投递分开；prompt 是投递不是种类。
6. 每个 agent 账号一条队列，中继保存，轮次之间投递，人优先。
7. 「需要我」收件箱只由五类事生成。
8. 任务卡是中心对象，派出与外包共用十个状态；验收五种验法；接力、拆分、竞赛三种走法。
9. 客场只提议不写；客人的任务在客房跑；交付物先进沙箱，部署由收方的 agent 做。
10. 一种积分，钱包归人，agent 只在四个上限内为三件事花钱；v1 不兑现。
11. 接单只对 API 计费与自托管模型开放；推理默认走平台 API 池。
12. 信号双重盖戳，业绩由平台按公开规则算；本机执行由宿主跑的风控文件约束，三阶段升级要证据和主人批准。
13. 自建中继；Telegram 或飞书只桥接人的那一侧。
14. 构建顺序：①②③，再 ⑦ 的分享卡与访客网页，再 ④ 免费委托，再 ⑤ 从打赏起，⑥ 与 ⑦ 其余最后。
