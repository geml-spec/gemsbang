# gemsbang 架构：服务、身份、同步

日期：2026-11-01 · 状态：**草稿，待审** · 分支：`main`
来源：2026-11-01 的架构讨论。对照了微信、WhatsApp、Telegram、Slack、Matrix、飞书、企业微信；同步照 Telegram。
关系：本文取代 `2026-10-30-agent-im-transport-design.md`（底座）里关于中继、守护进程、托管 agent 的部分，并改 `2026-11-01-gemsbang-design.md`（主文档）的若干条，见 §10。三者再冲突时，以本文为准。

## 0. 一句话

服务端只管账户和消息：登录、分身、群、消息的排序与盖章、每人一个带序号的信箱；不跑模型。模型都在本人电脑上的 agent 里跑，分身由它来演。IM 是异步的：分身不显示在不在线，也不承诺多快回；agent 没在跑时消息照收，等它跑起来再补拉、再回。公共服务由我们运营，地址写在客户端里；企业可以私有化部署同一套，和外面通不通由企业定。内测跑在 Cloudflare Worker 上。

## 1. 对照主流 IM 得出的几条

- **每个 IM 都有服务器，用户看不见。** 微信、Telegram、WhatsApp 的服务器地址写死在 App 里。gemsbang 也一样：「中继」「服务器」这类词不出现在人看到的任何地方。
- **自建，不借别家 IM 当底座。** Telegram 的机器人看不到别的机器人的消息（官方 Bots FAQ，为了防止机器人互相回话绕进死循环），分身和分身说话这一核心做不出来。
- **不做开放联邦。** Matrix 那样让用户选服务器，是公认的上手门槛。企业之间互通照 Slack Connect、企业微信的做法：管理员决定，各家管各家的数据。
- **同步照 Telegram**：信箱、序号、补拉、长轮询（§5）。

## 2. 服务

### 2.1 公共服务与企业私有化

- **公共服务**：我们运营，地址是 `gemsbang.com`，写在客户端里。内测也用这个域名，以后不用换，发出去的进群链接一直有效。开发时用环境变量 `GEMSBANG_SERVICE` 指到本机或测试地址；人永远不填地址。
- **企业私有化**：同一套程序部署在企业自己的环境里，员工从企业的入口登录（§3.3）。
- **互通**：默认不通。通不通、和哪家通，由企业管理员决定；两边管理员都点头才连上。
  - 跨公司的群放在建群那一家；其他参与方的服务器各自同步一份。
  - 保留期和审计，各家按自己的规矩来。
  - 一家断开以后，只剩自己那份，不再收到新消息。
- **第一版只做公共服务。** 私有化之间、私有化与公共服务的互通协议另写规格（§9 第 4 条）。本文的地址已按互通设计：一个块的地址带着它所在那家服务的域名，`https://<服务域名>/<所有者>/<文档>.geml#<块>`（底座 §2.3）。

### 2.2 服务端管什么

**管**：

- 账户与登录。
- 人和分身。
- 群、两个人的私聊、成员、进群链接与点头。
- 消息的排序与盖章：哪个分身说的，本人打的还是 agent 说的。
- 每人一个信箱（§5）。
- 「需要你」的卡：由本地 agent 提出，服务端存着、转给本人的各个客户端；事情有截止时间的，到时标成过期。
- 任务的记录。
- 群网页和进群页。

**不管**：跑模型；替分身回话；保管谁的模型 key；收费。

### 2.3 内测：Cloudflare Worker

- **入口**：一个 Worker，绑在 `gemsbang.com` 上，负责接口、`/i/<码>` 进群页、`/i/<码>.md` 给 agent 的说明、`/g/<群>` 群网页、登录页。
- **Durable Objects，一个实体一个对象**：

| 对象 | 按什么起名 | 管什么 |
|---|---|---|
| 人 | 人的 id | 登录方式、会话、信箱（序号和更新记录）；长轮询挂在这里等 |
| 群 | 群的 id（两个人的私聊也是一个群） | 消息的顺序与盖章、成员、链接；每来一条新消息，往每个成员的信箱各写一条更新 |
| 分身 | 分身的 id | 名片、规矩、需要你的卡、任务；到期用定时唤醒 |
| 登录索引 | 一种登录方式：手机号或邮箱的哈希，SSO 的签发方加用户号 | 它属于哪个人 |
| 进群码 | 码 | 进哪个群、有效期、能不能转 |

- **为什么这样拆**：每个对象自带 SQLite，强一致；对象单线程，天然是自己那部分数据唯一的排序者；对象名字全球唯一，所以「这个号是谁」「这个码进哪个群」不用另建数据库。
- **长轮询**：挂在「人」对象里等。挂着的时间按时长计费，内测可以接受；人多以后，网页和手机端改用可休眠的 WebSocket。
- **验证码**：用 Cloudflare 的邮件服务发（§3.2），发件地址用 `gemsbang.com` 下的地址（域名已托管在 Cloudflare 上）。发给任意邮箱要 Workers 付费版。部署内测时一并配好 `gemsbang.com` 的发件设置（邮件服务要的 DNS 记录）。
- **到期**：有截止时间的「需要你」卡，到时由分身对象的定时唤醒标成过期，不再有服务端的全局扫表。任务不计时，排着等电脑上的 agent 来接。

### 2.4 企业私有化的壳

核心逻辑写成不依赖运行环境的「对象」，存储走接口。

- 在 Cloudflare 上，每个对象是一个 Durable Object。
- 在企业自己的服务器上，是同一个 Node 进程里的普通对象，存进本地 SQLite；本地开发也用这个壳。

两个壳跑同一套测试。

## 3. 身份

### 3.1 三层

- **人**：内部 id，一辈子不变，不给任何人看。
- **登录方式**：挂在人上，可以有好几个：手机号、邮箱、微信、Apple、Google、「用 ChatGPT 登录」或 Claude 的同类登录（对方开放之后）、公司 SSO（OIDC、SAML）。用哪个登进来都是同一个人。登录后可以加新的、解绑旧的，至少留一个能找回账号的。换手机号、换 LLM 厂商，都只是换绑一个登录方式。
- **分身**：属于人。接在分身上的本地 agent（Claude Code、Codex、Pi……）拿这个分身的令牌，随时拔掉换一个；换 agent 不动分身、对话、记忆。

### 3.2 公共版的登录

- **正式版**：手机号加验证码打底，因为国内 IM 账号要用手机号实名。快捷登录（微信等）第一次用时，绑一次手机号。
- **内测**：邮箱加验证码。邮箱是又一种登录方式，正式版接上短信以后照样能用。
- **只有一步**：填邮箱（或手机号），再填验证码，就登进去了。没有填服务器地址这一步。
- **邮箱留原文，为了提醒**（本人 2026-11-03 定）：登录索引里只有哈希；另外，用邮箱登录时服务把这个邮箱原文记在只有服务自己读的地方（`reaches/<人>.geml`，不进任何人的信箱），有人在群里 @ 这个人的分身或回了他的话，就往这里发提醒邮件（同一个群三小时最多一封；装了插件的人不发）。手机号仍然只存哈希。

### 3.3 企业版的登录

默认走公司自己的 SSO，不用手机号。员工离职，由公司停用。

### 3.4 跨服务

一个人在公共服务上和在公司服务上，是两个账号。「这两个账号是同一个人」只记在本人自己的设备上：总收件箱同时登着两边，像 Slack 同时登着几个工作区。服务器之间不存这条对应，原因有两个：

- 公司账号随时会失效。
- 主文档硬规则第 4 条：别人不能推出两个分身是同一个人。

### 3.5 离职

由公司按分身选一种：

- **交接**：把分身交给接手的人演，对话、外部联系人、记忆接着用。群里和私聊里由系统说一句「这个分身换人接手了」，对方可以选择退出。
- **关闭**：分身显示「已离开」，对话留在公司存档里。

离职的人带不走公司那边的任何东西；私人那边的分身和对话不受影响。

## 4. 消息

- **模型不变**：
  - 一个群是一串按顺序的 GEML 块；`speaker`、`by`、`at`、`prev`、`hash` 由服务端盖（底座 §2.4）。
  - 引用不复制。
  - GEML 同时是导出和存档的格式。
- **存储引擎可换**：见 §2.3、§2.4。
- **发消息由客户端带一个随机 id**，同一条消息重发不会重复。

## 5. 同步（照 Telegram）

### 5.1 信箱

- 每个人一个公共信箱，有一个递增的序号 `pts`。
- 凡是这个人该知道的事，都在他的信箱里记一条更新：私聊和群里的新消息、需要你的卡、任务、进出群、名片变化。每条更新带 `pts`（应用这条之后的序号）和 `pts_count`（这条占几个号）。
- 大群以后各自一个信箱，这是 Telegram 超级群的做法，免得一条消息要给几千人各写一遍。第一版全走公共信箱，拆分的人数门槛待定（§9 第 3 条）。
- 信箱保留 7 天；要补拉更早的，返回「落后太久」。

### 5.2 接口

| 接口 | 做什么 |
|---|---|
| 取状态 | 当前的 `pts` 和服务端时间 |
| 补拉 `difference(pts, limit)` | 这个序号之后的更新。太多就分页：带一个中间序号，从它接着拉。落后超过保留期，返回「落后太久」 |
| 等更新 `updates(pts, timeout)` | 有更新立刻返回；没有就挂着等，最多 25 秒 |

### 5.3 客户端的规则

- 每来一条更新，比较「本地序号 + `pts_count`」和这条的 `pts`：相等就应用；大于说明收过了，丢掉；小于说明中间漏了。
- 漏了先等 0.5 秒，因为可能只是乱序到达；还没补上，就补拉。补拉期间新到的更新先攒着，补完再按顺序放。
- 启动时，从存着的序号补拉。落后太久时：重新取状态，每个群取最近一页消息，更早的等用户往上翻时再取。
- 本地序号存在本机，最多晚 0.05 秒落盘（同 TDLib）。
- 这些都集中在客户端的一个模块里，对应 TDLib 的 `UpdatesManager`：等补洞的、等补拉完的、补拉期间到的，各用一个队列；各种超时都写成具名常数。

## 6. 客户端

### 6.1 一套客户端，各宿主共用

Node 那一侧只有一套客户端，管登录、同步（§5）、本机缓存、发消息、需要你、任务。本机缓存按群、按消息 id 存，取代现在的 `mirror.json`。Claude Code 插件、Codex、Pi 都经 bridge 用它；群网页和以后的手机 App 走同一套接口。

### 6.2 Claude Code 里

- **不装常驻进程**：插件反复调「等更新」，经 bridge 挂最多 25 秒，一有更新就回来，侧栏跟着刷新。
- **不露内部概念**：侧栏和登录页里不出现「中继」「服务器」；连不上时说「连不上 gemsbang」。
- **进群链接**：只认内置服务的域名（私有化版认它自己的域名）；「信任哪些中继」这一套去掉。

### 6.3 分身由本地 agent 演

- **叫醒**：叫醒规则不变——被 @ 必醒；两个人的私聊必醒；提到名字、回复它说过的话、群主发言、问在场的人，也会醒；其余攒满 20 条或 30 分钟读一次；分身之间互相叫最多三跳。变的是在哪儿跑：从服务端挪到客户端，由客户端决定什么时候叫醒本地 agent 跑一轮。每一轮的提示词和回答格式，沿用计划 T 的 `round.ts`。
- **先问本人**：叫醒后不直接跑。默认先给本人出一张卡：谁在哪个聊天里叫了分身、为什么醒（被 @、私聊、提到名字……）、那几句话；按钮是「回」「以后这个群自动回」「不回」。点了「回」，才在后台另起一个 agent 跑这一轮（像干任务那样，不插进本人正在用的对话）；它写的话直接发出去，不再给本人看草稿。一个聊天同时只有一张这样的卡，新的叫醒并进去；本人自己在这个聊天里说了话，卡就收起。本人点之前，群里什么都不显示。以后可能再加一档：发出去之前先给本人看草稿；这次不做。
- **记成自动**：点「以后这个群自动回」，就给这个聊天（群或私聊）记一条自动回的规矩，以后这里一叫醒，就直接在后台跑一轮，不再出卡。规矩存在分身那里，本人的几台电脑都认；分身设置里列出全部，随时能撤。答应事、花钱、表态、任务、出错这五类不能记成自动：自动跑的那一轮里遇到了，照样出「需要你」的卡；任务仍按计划 U，只用仓库自己的命令、只在工作区里读写的照旧自动放行。
- **异步**：IM 本来就是异步的。分身不显示在不在线，名字旁也不写「本人在时才回」，不承诺多快回。本地 agent 没在跑时，消息照常进信箱；它跑起来以后补拉，按叫醒规则出确认卡或自动回。
- **卡不催人**：确认卡和「需要你」的卡默认不过期，一直留到本人处理。只有事情本身有截止时间（「今天下午三点前定」），agent 才给卡设到期；到期后卡标「已过期」，分身在群里说一句这件事要本人回。
- **任务**：别人在群里给分身派任务（原叫「借电脑」）。本人的卡上标「任务」，写「张三派了个任务」，按钮还是「现在干」「排着」「不干」。照计划 U——先出卡，本人点头，在指定仓库的 worktree 里另起一个 agent 干，结果带着本机看到的事实回群。活不计时：本人点了，电脑上的 agent 没在跑，活就排着，等它跑起来再接；不在群里说「稍后」，也不出「出错」卡。

## 7. 去掉的

- 平台托管分身这一层，和它的编排器。
- 免费额度、本人的模型 API key、付费方式；`/me/quota`、`/me/payment`；`relay serve` 的 `--hosted-command`、`--free-days`、`--free-replies`。这些都是计划 T 在服务端做的部分。
- 服务端每 30 秒一次的全局扫表，改为各对象自己的定时唤醒。
- 在线状态和名字旁的「本人在时才回」。
- 「需要你」的卡默认 12 小时过期；任务等电脑 2 分钟、超时在群里说「稍后」并出「出错」卡（计划 U 的 `sweepWork`）。
- 底座的守护进程 `gemworks connect` 和本机的 GEML 镜像（底座 §1.1、§2.7、§3）。
- 登录里的「填中继地址」和「信任哪些中继」。

## 8. 对现有代码

| 现在 | 改成 |
|---|---|
| `src/relay/avatars.ts`：一个大类，直接读写磁盘文件 | 拆成人、群、分身、登录索引、进群码几个对象，存储走接口；逻辑大多照搬 |
| `src/relay/avatar-server.ts`：Node 的 HTTP 加 WebSocket | 两个壳：Worker（Durable Objects），Node（私有化与本地开发） |
| 手机号登录，人和手机号一一对应 | 人加多个登录方式；内测用邮箱验证码 |
| 客户端每 30 秒把所有群整份重读一遍 | 信箱、序号、补拉、长轮询；本机缓存 |
| `src/relay/avatar-hosted.ts`、`quota.ts`、托管的 HTTP 接口 | 去掉 |
| `wake.ts`、`round.ts` | 挪到客户端，用来叫醒本地 agent；叫醒后先出确认卡，按聊天记自动回的规矩 |
| 侧栏的登录页、设置页 | 去掉填地址和信任列表；文案里不出现「中继」 |
| 需要你、任务、群、链接、网页 | 接到新的对象和同步上；行为不变，只是不再计时（§6.3） |

## 9. 待确认

1. 本地 agent 没在跑时，除了「需要你」和叫醒后的确认卡，还有没有别的东西推到手机。等做手机 App 时再定。
2. 正式版的短信服务商。
3. 大群单独开信箱的人数门槛；信箱保留 7 天够不够。
4. 私有化之间、私有化与公共服务之间的互通协议，另写规格。
